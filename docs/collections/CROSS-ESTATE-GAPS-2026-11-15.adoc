== Additional, underrepresented assurance layer

Meta-theory, independent proof checking, certificate checking and verified
proof-machine execution were not explicitly assigned a family in the
141-variant ledger. They are *not all synonyms* for automated proving:

* https://github.com/MetaRocq/metarocq[MetaRocq] — Rocq metatheory,
  verified type checking and erasure.
* https://github.com/digama0/lean4lean[Lean4Lean] — alternative Lean 4
  kernel implementation and ongoing metatheory; original-kernel derivation
  limits claims of implementation independence.
* https://github.com/ammkrn/nanoda_lib[nanoda] — Rust-based independent
  checking of Lean declarations; not a formally proved checker merely by
  being independent.
* https://cakeml.org/candle/[Candle] — machine-code-level verified HOL
  prover according to the project; specifically a stronger claim than an
  ordinary kernel replay.
* https://github.com/smtcoq/smtcoq[SMTCoq] and
  https://github.com/ufmg-smite/carcara[Carcara] — SMTCoq provides
  *certified checkers* for supported external proof witnesses, whereas Carcara
  is an independent Alethe-format checker not claimed to be formally verified;
  neither a certificate nor a proof-format label is automatically certified.
* https://www.cakeml.org/checkers.html[CakeML proof checkers], including
  https://github.com/tanyongkiam/cake_lpr[cake_lpr], and
  https://satcompetition.github.io/2026/output.html[SAT Competition 2026]
  checks (GRAT, VeriPB/CakePB) — proof-certificate validation paths with
  explicit input formats and verification boundaries.
* https://github.com/Deducteam/Dedukti[Dedukti] and
  https://github.com/Deducteam/lambdapi[Lambdapi] — logical frameworks
  and proof exchange. A checked translated proof does not automatically
  validate the translation of its original meaning.

The https://github.com/stuff-of-awe/awesome-provable/pull/18[awesome-provable
PR #18] was *merged prematurely on 2026-11-15* before all review findings
and latest-commit assurances were resolved. Its checker index exists, but
merging does not certify its conclusions, and a separate dedicated collection
has not yet been created.

== Recommended release groups

* *P0 — strengthen current coverage*: repair and enrich existing
  Agda, Coq/Rocq, Idris2, provable-code, Lean, Isabelle, Z3 and cvc5
  lists; demand canonical references, useful tutorials, and licence provenance.
* *P1 — high-value dedicated starters*: `awesome-acl2`,
  `awesome-dafny`, `awesome-why3`, `awesome-eprover`,
  `awesome-dedukti`, and a proof-certificate/checker family collection
  tentatively `awesome-proof-checking`. These serve estate use or clear
  interoperability/assurance needs.
* *P1 — related-family collections*: `awesome-automated-theorem-proving`,
  `awesome-sat-solvers`, `awesome-model-checking`,
  `awesome-protocol-verification`, and `awesome-constraint-solving`.
  Use family-level repositories where individual tools cannot support
  four useful introductory sections without padding.
* *P2 — specialist collections*: follow the 80 existing Planned rows
  in link:CATALOGUE.adoc[the ledger], prioritising public research use,
  maintainer availability and original examples, not repo proliferation.
* *Internal*: the 41 declared estate type disciplines belong in a
  shared type-systems reference until there is a real independent public
  implementation to document; avoid 41 empty "awesome" repos.

Before releasing a repo, document the upstream awesome-list survey, project
home, canonical docs, tutorial, reference, worked example, community channel,
licence, curator, review date and maintenance caveats. A name alone is not
completion.

== Trust and operational gates

An ECHIDNA `ProverKind` declaration or a source adapter only demonstrates
source-level coverage. In particular,
https://github.com/hyperpolymath/echidna/blob/main/meta-checker/README.adoc[the
ECHIDNA meta-checker] explicitly distinguishes proof of its Agda model from
proof that the Rust pipeline implements that model. Do not use this index to
upgrade such claims.

Promote a proposed collection to Existing only once its repository, original
content, attribution, and review evidence are actually present. Treat merging
as complete only once the latest-commit checks are green and relevant review
threads are addressed and resolved. Never automatically merge or waive gates.
